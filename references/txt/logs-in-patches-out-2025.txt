Abstract
Research on automated vulnerability repair often requires extensive program analysis and expert input, making it challenging to deploy in practice. We propose S AN 2PATCH, a system
that generates patches using only sanitizer logs and source
code, eliminating the need for costly program analysis or manual intervention. S AN 2PATCH employs multi-stage reasoning with Large Language Models (LLMs) to decompose the
patching process into four distinct tasks: vulnerability comprehension, fault localization, fix strategy formulation, and patch
generation. Through tree-structured prompting and rigorous
validation, S AN 2PATCH can generate diverse, functionallycorrect patches. Evaluations on the VulnLoc dataset show that
S AN 2PATCH successfully patches 79.5% of vulnerabilities,
surpassing state-of-the-art tools like ExtractFix (43%) and
VulnFix (51%) by significant margins. On our newly curated
S AN 2V ULN dataset of 27 new vulnerabilities from various
open-source projects, S AN 2PATCH achieves a 63% success
rate, demonstrating its effectiveness on modern security flaws.
Notably, S AN 2PATCH excels at patching complex memoryrelated vulnerabilities, successfully fixing 81.8% of buffer
overflows while preserving program functionality. This high
performance, combined with minimal deployment requirements and elimination of manual steps, makes S AN 2PATCH a
practical solution for real-world vulnerability remediation.

Introduction

Software projects contain various vulnerabilities that can lead
to significant losses [4, 17]. Such damages have been increasing annually, with the total loss projected to reach $10.5
trillion USD by 2025 [28]. Although automated tools such
as fuzzing [24] have been developed to identify these issues,
patching the discovered vulnerabilities still relies heavily on
human experts. This reliance exists because, unlike vulnerability detection, patching requires a comprehensive understanding of the entire codebase, making automation difficult.

In addition, vulnerability patches must fix security flaws without changing the existing functionality of the project. Therefore, generating correct patches requires the sophisticated
reasoning processes of domain experts, posing a significant
challenge to automation.
Automated program repair (APR) has emerged as a promising solution for addressing software defects, with significant research advances in recent years [15, 46]. While early
APR approaches focused on general bug fixing [19, 20, 29,
34], specialized techniques for vulnerability patching have
demonstrated superior performance in addressing security
flaws [13, 48]. The emergence of Large Language Models
(LLMs) has further accelerated this field, with several studies exploring LLM-based approaches for vulnerability repair [12, 32, 42, 48, 51]. These studies leverage LLMs’ advanced code understanding capabilities, showing promising
results that suggest even greater potential as LLM technology
continues to evolve [11, 43].
However, existing approaches face two critical limitations
that hinder fully automated security patch generation. First,
existing tools require substantial human intervention in the
repair process. Many systems, such as VulnFix [48] and VulRepair [12], depend on manually provided information about
patch locations or vulnerable code snippets. This dependency
on human input creates a significant bottleneck in achieving complete automation. Additionally, most studies have
focused solely on patch generation, neglecting the crucial
step of fault localization [41], which is essential for a fully
automated solution. Second, existing methods rely heavily on
resource-intensive program analysis techniques. For instance,
VulnLoc [38] and VulnFix [48] employ fuzzing-based methods for fault localization and patch generation, while ExtractFix [13] and CPR [37] utilize symbolic or concolic execution.
These dynamic analysis approaches introduce significant challenges in practice. They necessitate complex environmental
setups and instrumentation, which substantially increases the
complexity of deployment and maintenance. Moreover, these
methods consume considerable computational resources and
processing time.

novel approach to automated vulnerability repair that operates solely on sanitizer logs from vulnerability detection. By
eliminating the need for complex program analyses or additional developer input, S AN 2PATCH autonomously handles the entire repair pipeline—from fault localization to
patch generation—addressing the key shortcomings of existing methods.
At the core of S AN 2PATCH lies our utilization of LLMs for
the efficient generation of patches. Specifically, we structure
the process into four stages: Vulnerability Comprehension,
Where-to-Fix, How-to-Fix, and Candidate Generation, and integrate Tree of Thought [45] prompting. We further devise an
algorithm that extracts and provides code snippets to the LLM,
balancing minimal snippet size with essential code context.
We evaluate S AN 2PATCH on two comprehensive datasets
to demonstrate its effectiveness in real-world vulnerability repair. First, on the VulnLoc dataset [38], S AN 2PATCH achieves
a 79% success rate (31 out of 39 vulnerabilities), significantly
outperforming ExtractFix’s 43% success rate (9 out of 21) and
VulnFix’s 51% success rate. Our detailed analysis shows that
S AN 2PATCH successfully patches 7 out of 9 vulnerabilities
that ExtractFix could fix while also addressing 10 out of 12
vulnerabilities that ExtractFix failed to repair.
In addition, we conduct an assessment on our newly curated S AN 2V ULN dataset, comprising 27 new and unseen
vulnerabilities from various open-source projects—including
complex issues such as buffer overflows (e.g., CVE-202226981) and memory corruption bugs (e.g., CVE-2022-31783).
S AN 2PATCH successfully generates valid patches for 17 of
these 27 vulnerabilities (63% success rate).
Particularly noteworthy is S AN 2PATCH’s performance on
memory-related vulnerabilities, achieving an 81.8% success
rate on buffer overflow cases (18 out of 22). Furthermore,
S AN 2PATCH maintains program functionality in 81.8% of
the patched buffer overflow cases, demonstrating its ability
to generate precise fixes that preserve intended behavior.

• We introduce S AN 2PATCH, an LLM-based automated

developer input or sophisticated static analyses.
• We propose a four-step patch generation pipeline supplemented by Tree of Thoughts prompting, significantly
enhancing the LLM’s reasoning capacity at each stage.
• We develop an optimized algorithm to extract and deliver concise yet context-rich code snippets and function
context to the LLM, improving both performance and
scalability.
• Through comprehensive evaluations across both the
VulnLoc benchmark and our novel S AN 2V ULN dataset,
we demonstrate S AN 2PATCH’s superior performance

S AN 2PATCH Design

3.1

System Overview

S AN 2PATCH is an end-to-end system for automated vulnerability repair that leverages LLMs to transform sanitizer logs
into validated security patches. As illustrated in Figure 6, the
system operates through two main phases: Patch Generation
and Patch Validation, with several key components working
in concert to enable reliable and efficient patch creation.
The Patch Generation phase implements a novel four-stage
pipeline designed to mirror expert developers’ vulnerability
repair workflow. In the Vulnerability Comprehension stage,
LLMs analyze the sanitizer output to understand the root
cause and characteristics of the vulnerability. This understanding informs the Where-To-Fix stage, where LLM reasoning is

4404

34th USENIX Security Symposium

employed to identify precise code locations requiring modification, similar to traditional fault localization approaches. The
How-To-Fix stage then formulates repair strategies according to the type of vulnerability and fix location. Finally, the
Candidate Generation stage combines these insights to create
candidate patches that address the identified vulnerability.
To ensure robust patch generation, S AN 2PATCH incorporates advanced techniques. The system employs Tree of
Thoughts (ToT) [45] prompting, enabling the exploration
of multiple reasoning paths simultaneously instead of a
single line of thought. This is complemented by a selfevaluation [44] mechanism that evaluates and prunes reasoning paths, optimizing the exploration of solutions while
maintaining patch quality. Additionally, a specialized Context
Retriever module provides relevant code context to the LLM,
balancing information completeness with token limitations.
The Patch Validation phase implements rigorous quality
control through a series of automated checks. Each candidate
patch undergoes sequential verification steps: build verification ensures syntactic correctness, vulnerability testing confirms the security fix, and functionality preservation checks
validate that the patch maintains the program’s original behavior. This comprehensive validation ensures that only patches
meeting all quality criteria are selected as final solutions.
These components create a robust framework that automatically generates and validates security patches, eliminating the
need for manual intervention or advanced program analysis
techniques. As shown in Figure 6, the Patch Generation phase
uses only sanitizer logs and source code. The Patch Validation
phase additionally requires a PoC input to trigger the vulnerability, along with the project’s build instructions, execution
script, and functionality tests. These inputs are required to
run S AN 2PATCH end to end.

3.2

Multi-Stage Patch Generation

Generating vulnerability patches requires complex reasoning and domain expertise that can challenge even advanced
LLMs. Drawing from prior research [49] on breaking down
complex problems, S AN 2PATCH implements a carefully structured four-stage pipeline that mirrors the systematic approach
taken by expert developers. This decomposition aligns with
established APR methodologies while incorporating critical
aspects of real-world vulnerability remediation. Traditional
APR primarily focuses on two phases: Where-To-Fix and
(Patch) Candidate Generation. S AN 2PATCH expands upon
this foundation by adding two crucial stages that reflect actual
developer workflows: Vulnerability Comprehension and HowTo-Fix. These additional stages enable a more systematic and
thorough approach to vulnerability repair.
Vulnerability Comprehension. In this initial stage,
S AN 2PATCH performs in-depth analysis of the sanitizer log
to understand the vulnerability’s fundamental characteristics.
Unlike typical scenarios where developers have access to detailed vulnerability reports, S AN 2PATCH must infer critical
information—including root cause, vulnerability type, and
potential impact—solely from the sanitizer output. This understanding forms the foundation for subsequent stages, much
like how developers begin their repair process by thoroughly
analyzing the security flaw.
Where-To-Fix. With clear vulnerability information in
place, S AN 2PATCH identifies optimal code locations for implementing security fixes, corresponding to the fault localization phase in traditional APR methods [41]. The system
primarily relies on crash stack traces from sanitizer logs,
which contain crucial information about memory access patterns, heap allocations, and free operations. For example, heapbased buffer overflow traces typically include both memory
access and heap allocation information, while UAF vulnerabilities present additional memory-free operation details.
S AN 2PATCH leverages an LLM-driven process to analyze
these diverse stack trace patterns, supplemented by the context
retrieval algorithm that provides the necessary code context
for accurate analysis.
The system’s approach extends beyond simple stack trace
analysis. Although stack traces often indicate the immediate crash location, LLM can identify alternative fix locations
based on broader vulnerability context and code structure analysis. This flexibility is particularly important for complex vulnerabilities that require multi-hunk patches—modifications
across multiple code locations. In such cases, S AN 2PATCH
can identify and manage multiple fix points simultaneously,
ensuring comprehensive vulnerability remediation while
maintaining code consistency.
How-To-Fix.
Before generating patch candidates,
S AN 2PATCH formulates comprehensive repair strategies
based on the vulnerability information gathered in the

USENIX Association

previous stage. In this crucial step, the LLM generates
specific fix guidelines by analyzing the vulnerability’s
root cause, type, and characteristics identified during the
Vulnerability Comprehension stage. This strategic planning
stage is essential for avoiding one of the common pitfalls
in automated repair: the tendency to generate patches that
merely replicate patterns from training data.
The fix strategies developed in this stage serve as a foundation for generating diverse and effective patches. By establishing clear repair guidelines before attempting specific
code modifications, S AN 2PATCH can explore a broader range
of potential solutions rather than defaulting to common fix
patterns. This approach enables the system to generate more
effective, targeted patches while ensuring they directly address the identified vulnerability characteristics. The resulting
fix guidelines significantly influence subsequent stages, ultimately leading to more effective and varied patch candidates.
Candidate Generation. The final stage synthesizes insights
from previous stages to produce concrete fixes. With the fix
location already identified, S AN 2PATCH provides the LLM
with curated code context from the Where-To-Fix stage, along
with vulnerability details and repair strategies from earlier
stages. To ensure precise modifications, the system augments
the code context with clear markers, including comments identifying the exact fix locations. Instead of using diff directly,
which can complicate line numbering for LLMs, the system
generates fully modified code files first. These files are then
processed by dedicated tools to create accurate patch files.
Each patch candidate undergoes thorough validation: build
verification ensures syntactic correctness, PoC testing confirms the fix’s effectiveness, and functionality testing verifies
that the original program behavior is preserved. By generating fully modified code instead of diff patches, S AN 2PATCH
avoids line-numbering issues common with LLMs. After modification, a patch generation tool creates the final accurate
patch file.
Once the patch is generated, it is applied to the project, and
the verification process begins. First, the modified project is
built to check for any syntax or build errors. If any build errors
occur, the error messages are fed back to the LLM, guiding
it in generating corrected code. If the build errors cannot
be resolved after several iterations, the patch is rejected. If
the build succeeds, the patch is tested with the PoC input to
ensure the vulnerability has been fixed. If the sanitizer still
detects the crash, the patch is rejected. For patches that pass
the security test, a final functionality test is conducted using
the project’s unit tests to verify that the patch does not affect
the original functionality. Only patches that successfully pass
all tests are selected as the final patch.

Furthermore, the generated rationale is essential for verifying whether the response is correct. This is particularly
important in techniques such as Chain of Thought (CoT)
prompting, where rationales guide the reasoning process. In
CoT, the rationale for the previous step is utilized in the next
step. Additionally, in S AN 2PATCH, these rationales are passed
to subsequent stages and serve as valuable extra information
for further reasoning. For example, the vulnerability details
inferred in the Vulnerability Comprehension stage are leveraged in later stages, where not only the results of the inference
are passed but also the rationale for the inference. This helps
to enhance the reasoning results of the LLM and increase the
memory of previous steps.
CoT-SC. The results of each subtask in the patching process
are used in subsequent stages. Therefore, if an incorrect result
is generated at any stage, especially at an earlier stage, such as
Vulnerability Comprehension, this may significantly reduce
the overall quality of the patching process.
To address this issue, S AN 2PATCH applies Chain of
Thought (CoT) [40] and Self-Consistency [39] techniques
to the first subproblem to improve the reliability of the LLM’s
answers. CoT-SC involves prompting the LLM to generate
multiple responses and then selecting the most consistent one.
Initially, the LLM generates K different responses through
the CoT process. These are then processed by an aggregation
prompt, which evaluates each candidate and selects the most
consistent one. This selected answer becomes the final output
of the stage. This approach helps reduce the risk of the LLM
providing probabilistically incorrect answers. The hyperparameter K, which specifies the number of answers generated
simultaneously, is adjustable. In this work, we set K to 3.
ToT. Tree of Thoughts (ToT) prompts can provide better
performance than simple Chain-of-Thought by generating
diverse candidates of answers [45]. ToT reasoning works similarly to CoT by performing reasoning in sequential steps.
However, unlike CoT, it explores multiple potential solutions
at each step, allowing a diverse search for possible answers
without aggregating them into a single answer before continuing to the next stage.
The ToT process consists of three main steps: Branching,
Scoring, and Pruning. In the Branching step, the LLM generates K new candidate results based on the outcomes of the
previous inference step. This process allows the model to
explore diverse reasoning paths, ensuring a comprehensive
search for potential solutions. However, as the inference progresses, the number of nodes can grow exponentially, making
it crucial to retain only the most optimal nodes for further reasoning. To achieve this, in Scoring step, a self-evaluation [44]
mechanism using the same LLM is employed to assess and
assign scores to each reasoning node. Based on these scores,
ToT retains the top N nodes through selection criteria. This
Pruning step helps focus on the most promising reasoning
paths while optimizing computational efficiency.

In S AN 2PATCH, ToT prompting is applied across the
Where-To-Fix, How-To-Fix, and Patch Generation stages. During the Branching step, the LLM generates K new reasoning
nodes based on the results of the previous stage. For example,
in the Where-To-Fix stage, the LLM selects five potential fix
location candidates by analyzing the inferred root cause and
type of vulnerability from the earlier stage. To maximize diversity in the generated responses, the LLM is prompted to
produce all K candidates in a single query, ensuring a broader
exploration of potential solutions.
In Scoring step, the generated nodes undergo selfevaluation using evaluation prompts. During this process,
the evaluation LLM not only assigns a score to each node but
also provides a confidence level for the given score, enhancing the reliability of the evaluation. The final score of a node
is determined using the formula: reliability_score = score ×
(1 + 0.1 × con f idence). Both the score and confidence values
are restricted to integers within the range of 1 to 10.
Finally, once the self-evaluation process determines each
node’s score, only the optimal nodes are selected for further
reasoning. Two approaches are used to select optimal nodes: a
“greedy” method that retains the top N nodes with the highest
scores and a “sampling” technique that performs weighted
sampling based on the assigned scores.
In this study, the values of K and N were set to 5 and
3 for the Where-To-Fix stage, and 3 and 1 for the How-ToFix stage. Scoring and Pruning steps were not applied in
the Patch Generation stage. Instead, three patch candidates
were generated per node and evaluated through validation.
The selection of the optimal nodes was performed using a
“sampling” technique.

3.4

Code Context Management

Managing code context is crucial for LLM-based vulnerability
repair, as it directly impacts the quality of generated patches.
S AN 2PATCH implements two complementary approaches to
provide comprehensive yet focused code context: AST-based
code segment extraction and function-level context analysis.
Code Segment Extraction LLMs face inherent token limitations that make it impractical to process entire codebases.
However, the balance of context is critical—too much code
can dilute the LLM’s attention, while too little can lead to
incorrect patches. For example, missing variable declarations
can prevent proper boundary check implementation during
buffer overflow repairs.

Evaluation

In this section, we evaluate the performance of the proposed
S AN 2PATCH framework through various experiments. To
guide the evaluation, we set five key research questions:
• RQ1: How does S AN 2PATCH’s performance compare to
other vulnerability repair tools?
• RQ2: Can S AN 2PATCH practically patch recent or new
vulnerabilities?
• RQ3: How does patching performance vary across different LLM models?
• RQ4: How effective is S AN 2PATCH in generating functionally correct patches?
• RQ5: Can S AN 2PATCH successfully patch a variety of
vulnerability types?
VulnLoc Benchmark. We evaluated S AN 2PATCH using the
VulnLoc dataset [38], which contains 43 real-world vulnerabilities from nine major open-source projects, including binutils, ffmpeg, libxml2, and libtiff. The dataset encompasses five
vulnerability types, ranging from buffer overflows and integer
overflows to more complex use-after-free vulnerabilities.
For our evaluation, we compiled all projects with appropriate sanitizer instrumentation and executed them with
PoC inputs to generate crash logs. Four vulnerabilities
(bugchrome-1404, CVE-2017-9992, CVE-2016-3186,
CVE-2016-5314) were excluded as they could not be
reproduced with sanitizer instrumentation, resulting in a final
evaluation set of 39 vulnerabilities.
S AN 2V ULN Benchmark. To evaluate S AN 2PATCH’s ability to handle novel vulnerabilities, we created S AN 2V ULN, a
benchmark focusing on recent and previously unseen security
flaws. This addresses a key limitation of the VulnLoc dataset,
which contains vulnerabilities only from 2018 and earlier that
could exist in LLM training data.
We constructed S AN 2V ULN by systematically collecting
and validating recent vulnerability reports from public GitHub
issues, identified through sanitizer log keywords. Each vulnerability was reproduced in a controlled environment matching
the VulnLoc setup. The final dataset contains 27 vulnerabilities from four open-source projects. Of these, 11 vulnerabilities were published after August 2024, ensuring they fall outside the training period of the LLM used in our experiments.
Furthermore, 12 vulnerabilities in the dataset currently lack official fixes, providing an authentic test of S AN 2PATCH’s ability to generate novel patches. For consistency in evaluation,
we standardized the dataset format to align with VulnLoc. The
Appendix provides detailed information about S AN 2V ULN.
Implementation We implemented S AN 2PATCH in Python
3.10, leveraging several key frameworks. The LangChain
package [7] enabled seamless integration with LLM APIs,

including GPT, Claude, and Gemini. For structured prompt engineering, we used LangGraph [2] to organize our four-stage
patch generation pipeline as interconnected subgraphs, forming a unified processing workflow. LangSmith [3] provided
comprehensive logging and debugging capabilities, allowing
us to optimize prompts and handle edge cases effectively.
Validation We validated each generated patch through a
three-stage process. First, we confirmed that the patched
project compiled successfully. Second, we reran the original proof-of-concept input to ensure that the vulnerability
no longer triggered a crash. Third, we conducted functionality testing using project-specific unit tests where available.
Functional tests are detailed in Appendix B.
After conducting automated tests, we manually validated
every patch that passed the automated tests. Two security experts, each with over eight years of experience in vulnerability

patch that passed automated testing. Each patch was categorized into one of four labels: Correct (developer-matched),
when the patch was semantically identical to the developer’s
fix; Correct (alternative), when the patch differed from the
developer’s fix but resolved the general cause of the vulnerability without changing the program’s functionality; Incorrect (failed some test cases), when the patch did not address
the underlying cause and only prevented specific PoCs; and
Incorrect (failed all test cases), when the patch was entirely
incorrect, such as simply removing vulnerable code. Disagreements were resolved through structured discussion. Details
and illustrative examples of manual validation are included in
the supplementary material.
Evaluation Environment. All experiments were conducted
in a 64-bit Ubuntu 22.04 environment. The hardware used
for the experiments comprised an Intel Xeon Gold 5218 CPU
with 32 cores (2.30 GHz) and 64 GB of RAM. Throughout
the experiments, only OpenAI, Anthropic and Google LLM
models were utilized, and no GPU resources from the server
were employed. Unless otherwise stated, the default LLM
model used was OpenAI’s “gpt-4o-2024-08-06” model.

4.1

RQ1. Superiority of S AN 2PATCH

To evaluate the performance of S AN 2PATCH, we compared
it with existing vulnerability repair tools for C language programs. S AN 2PATCH was tested against VulnFix [48] and
ExtractFix [13], both focused on patching vulnerabilities in C
programs. VulnFix performs only patch generation, providing
the patch location without fault localization, whereas ExtractFix handles both fault localization and patch generation. The
results for VulnFix and ExtractFix were taken directly from
their respective papers. For ExtractFix, only a subset of the
Vulnloc benchmark was tested in the original study, so we
included results for those specific datasets. Neither study conducted functionality tests; patches were considered successful

USENIX Association

if they matched or were semantically equivalent to the developer’s patch. We applied the same criteria in our comparison
and considered VulnFix successful if either of its two backends generated a valid patch.
We also conducted a comparative analysis with recent
LLM-based patch generation studies, using VulRepair [12]
and VulMaster [51] as baselines. Unlike S AN 2PATCH, these
approaches do not perform fault localization but instead generate patches based on the vulnerable code snippet and its
CWE-formatted vulnerability type. The comparison focused
solely on patch generation performance. Developer patches
from our dataset were used to extract relevant code snippets
for testing, with the ground truth CWE ID provided as input. Special tokens were inserted around the fix location in
the code, and the generated patches were manually evaluated
against the developer patches as ground truth.
To assess the impact of our contributions, we conducted
experiments under different settings by adjusting prompting
techniques and context retriever configurations. In the Zeroshot configuration, the process involved two steps similar to
[32]: selecting a single fix location based on the sanitizer
output and extracting the corresponding code segment for
the LLM. In the CoT configuration, our problem decomposition approach was applied without branching, with prompts
structured in a sequential CoT format.
In the No Context setting, S AN 2PATCH’s ToT reasoning
was applied while disabling the context retriever. Without the
context retriever, the LLM received limited function-related
information, as the code snippet was extracted by including
(MAX_LINE + MIN_LINE)/2 lines both before and after
the target line, ensuring a consistent number of surrounding
lines instead of relying on AST-based parsing.
To ensure fairness, the context retriever was also disabled
in the Zero-shot and CoT configurations. The No Context and
original S AN 2PATCH settings were tested up to five times to
evaluate their patch generation success. Since S AN 2PATCH
generates up to nine patch candidates in a single execution
via ToT prompting, the Zero-shot and CoT experiments
were conducted nine times more than the S AN 2PATCH
experiments. The results of all experiments for RQ1 are
summarized in Table 1.
First, the performance comparison between VulnFix
and ExtractFix is as follows. As shown in Table 1,
S AN 2PATCH outperformed the other tools. Compared to VulnFix, S AN 2PATCH successfully patched eleven more vulnerabilities in total. Considering that VulnFix operates with
the patch location already provided, this demonstrates a notable difference in performance. In particular, S AN 2PATCH
performed better in addressing buffer overflow vulnerabilities, successfully patching 18 out of 22 cases, while VulnFix
patched only 10. This is because the LLM can accurately infer
the buffer size and generate appropriate constraints.
S AN 2PATCH achieved a higher success rate than ExtractFix, although the datasets are not identical. S AN 2PATCH

patched 31 out of 39 vulnerabilities for a success rate of
79.5%. Considering only the 21 vulnerabilities in ExtractFix’s dataset, S AN 2PATCH successfully patched 17 out of 21
vulnerabilities for a success rate of 81%, compared to ExtractFix’s 42.9% (9 out of 21). A detailed comparison revealed
that S AN 2PATCH successfully patched 7 out of the 9 vulnerabilities that ExtractFix patched while also patching 10 of
the 12 vulnerabilities that ExtractFix failed to patch. This
demonstrates S AN 2PATCH’s ability to address vulnerabilities
that traditional approaches cannot.
Compared to VulRepair and VulMaster, which are LLMbased patch generation tools, S AN 2PATCH demonstrated significantly better performance. Both VulMaster and VulRepair require the fix locations for code patches. Three items
from the VulnLoc benchmark were excluded due to the difficulty of extracting fix locations from the corresponding developer patches. As a result, the evaluation was conducted
on the remaining 36 items. VulMaster and VulRepair successfully patched only 2 and 1 vulnerabilities, respectively.

from data leakage rather than generalization ability.
The performance of VulRepair and VulMaster has declined
in terms of exact match accuracy compared to the results reported in their paper. This decline is attributed to the issue of
label leakage. Although the original VulMaster removed identical samples between the training and test datasets, we found
that they did not completely eliminate similar data samples.
In the VulMaster test set, 7.8% of the answers were identical
to those in the training set. Additionally, when comparing
code samples based on Jaccard Similarity of words, 15.8% of
the samples exceeded a similarity score of 0.7.

CoT, and No Context configurations patched 21, 22, and 24
vulnerabilities, while S AN 2PATCH successfully patched 31.
Notably, S AN 2PATCH outperformed the Zero-shot approach,
which relies solely on the LLM’s inherent reasoning, by patching 10 more vulnerabilities. These results underscore the significant impact of the proposed ToT prompting and Context
Retriever on improving LLM-based vulnerability patching.

S AN 2PATCH achieved a 79.5% patch success rate
(31/39 vulnerabilities), significantly outperforming ExtractFix (43%) and VulnFix (51%). Our approach with
ToT prompting and context retrieval showed particular strength in handling buffer overflows (18/22 cases),
demonstrating superior performance over both traditional

5.1

Discussion
Limitation of S AN 2PATCH

S AN 2PATCH is limited to generating patches for vulnerabilities that are detected by a sanitizer. Vulnerabilities that cannot
be detected by any sanitizer (e.g., the use of weak cryptographic algorithms [26] or authentication bypasses [25]) are
fundamentally unpatchable. Moreover, in this work, we focus on AddressSanitizer [36] and UndefinedBehaviorSanitizer [23]. Therefore, vulnerabilities detectable only by other
sanitizers, such as race conditions [27], which can be identified by ThreadSanitizer [22], are outside the scope of our

USENIX Association

evaluation and require further study.
S AN 2PATCH’s patch validation process also has some limitations. First, in the vulnerability test, only a single PoC is
used to test each vulnerability, which means that new vulnerabilities introduced by a patch may go undetected. Although
fuzzing could help mitigate this issue, achieving sufficient
coverage and reliable results requires running fuzzers for an
extended period, which is often not practical. Additionally, in
the functionality test, we rely on the project’s existing unit
tests. If the unit test coverage is incomplete, the accuracy of
the functionality test may be significantly reduced. To address these limitations, we performed manual validation in
this work; however, a more accurate and efficient functional
testing process is still needed.

5.2

Analysis of Failure Cases

We carefully analyzed the cases where patching failed. As a result, we identified the following reasons for failure. Examples
of failed patches can be found in the supplementary material.
Inaccurate Vulnerability Classification In several cases,
we observed that S AN 2PATCH incorrectly identified the
vulnerability type during the first stage, Vulnerability Comprehension. Most sanitizer logs provided sufficient descriptions
of the vulnerabilities, enabling the LLM to accurately
determine the types of vulnerabilities. However, a few logs
reported bug types that differed from the actual root cause,
causing the LLM to misunderstand the vulnerability. Since
this incorrect information propagates through subsequent
stages, it leads to incorrect patch generation, ultimately
preventing successful patches.
Challenges in Fault Localization S AN 2PATCH’s fault localization relies on stack traces. However, some vulnerabilities exhibit distinct characteristics, where the root cause lies
far from the stack trace. Therefore, in such cases, reasoning
in the Where-To-Fix stage often failed. For example, in CVE2018-19664, which all models failed to patch, the vulnerability is triggered by a function pointer call. Developers fixed
this by modifying the function pointer’s assignment, which is
far from the bug point. As a result, S AN 2PATCH was unable
to generate a successful patch. Similarly, for CVE-2016-8691,
another vulnerability that the model failed to patch, simply
fixing the location where the divide-by-zero occurs is insufficient; addressing the underlying root cause is necessary to
prevent further divide-by-zero vulnerabilities. Similarly, for
two UAF vulnerabilities — CVE-2018-8806 and CVE-20188964 — where S AN 2PATCH also failed to generate patches,
it is necessary to address their underlying root causes rather
than simply patching the crash location indicated by the stack
traces.
Limitations of Single-Location Fixes In S AN 2PATCH’s
Where-To-Fix stage, multiple fix locations can be selected at
once, but in most cases, the LLM tended to choose only a

USENIX Association

single vulnerable code region. Unfortunately, when dealing
with more intricate vulnerabilities, modifying only a single
location is not sufficient.
Incorrect Code Modifications Even when the LLM fully
understood the vulnerability and correctly identified the fix
location, it sometimes failed during Candidate Generation.
Most of these failures involved generating completely invalid
code, such as introducing incorrect constraints. In other cases,
the generated code was insufficient, addressing only specific
scenarios. For example, in CVE-2017-6965, the sanitizer log
showed a buffer overflow on a buffer of size 157 bytes. The
LLM used this detail to add a check for buffers smaller than
157 bytes, but the actual buffer size is determined at runtime.
Similarly, for CVE-2013-7437, the LLM added an arbitrary
large upper bound, resulting in a patch that only addressed the
specific PoC. On the other hand, some patches introduced too
many boundary checks, making the code overly restrictive
and causing functional test failures.
Syntactic and Structural Errors in Patch Code In some
cases, the LLM generated patches with basic syntax errors,
most often mismatched curly braces, especially in lowerperforming models. Post-processing resolved some errors,
but incomplete code blocks and unexpected formatting still
caused build failures. The LLM sometimes returned only partial edits despite instructions to generate complete code, or
defined new functions within provided blocks, which often
led to failures in vulnerability or functional tests.
Superficial Fixes That Bypass the Real Issue Another reason for patch failures was that the LLM sometimes attempted
to bypass vulnerabilities through superficial fixes. For example, it occasionally removed entire functions or important
logic, thereby avoiding the vulnerability trigger without addressing the root cause.

5.3

Code Context Trade-off

In S AN 2PATCH, we primarily provide code surrounding the
stack trace entries identified in the sanitizer log, parsed using
an AST-based approach. This decision was based on experimental results indicating that supplying excessive context
can actually hinder the LLM’s ability to accurately select
the correct fix location. When we provided program slicing
or inter-procedural results to the LLM, it frequently chose
irrelevant locations during fault localization, leading to lowerquality patch candidates. By restricting the input to code near
the stack trace — where the root cause is most likely to reside
— S AN 2PATCH was able to improve overall patch success
rates. Our design aligns with studies showing that relevant,
focused information is more useful for patch generation [31].
Furthermore, research highlights the importance of local context for effective reasoning [33], indicating that targeted code
context outperforms excessive code context.
Nonetheless, there are cases where the root cause does

34th USENIX Security Symposium

4413

not appear in the stack trace. For example, in CVE-20168691 and CVE-2018-19664, the functions modified by
the developer’s patch are not included in the stack trace.
Focusing on code regions close to the stack trace generally
improves efficiency and relevance, but may fail to capture
vulnerabilities needing more thorough root cause analysis
and expanded context. This underscores the balance between
targeted focus and broader coverage.

5.4

Factors Influencing Performance

The effectiveness of S AN 2PATCH is shaped by several key factors. One primary consideration is the potential influence of
training data, as LLM-based approaches may perform better
on vulnerabilities similar to those in their training sets. Previous research, such as VulMaster, demonstrated this effect,
showing higher accuracy for known vulnerability patterns. We
addressed this concern by carefully excluding vulnerability
identifiers and temporal information from our experiments,
forcing S AN 2PATCH to rely on fundamental reasoning rather
than pattern matching. The quality of crash analysis from sanitizer tools emerged as another crucial factor. Our use of GCC
AddressSanitizer logs provided detailed crash information
that enhanced S AN 2PATCH’s patch generation capabilities.
This observation suggests that advances in crash analysis tools
could further improve automated patch generation, mirroring
how human analysts benefit from detailed crash information.

5.5

Vulnerability-Specific Performance

S AN 2PATCH showed varying effectiveness across vulnerability types, excelling in buffer overflows and integer-related
issues but struggling with UAF vulnerabilities. This highlights
the need for more advanced methods to address complex
memory-related issues, particularly those requiring a deeper
understanding of memory lifecycle patterns. These results
suggest promising directions for future research, including
specialized strategies for challenging vulnerabilities.

Related Work

6.1

Automated Program Repair (APR)

Several studies in APR have specifically focused on patching
security vulnerabilities [15]. One such approach is SenX [16],
which generates patches for vulnerabilities by leveraging
human-specified, vulnerability-specific safety properties. Another notable method is CPR [37], which co-explores both
patch and input spaces through concolic path exploration, effectively reducing overfitting patches and improving repair
correctness. ExtraFix [13], on the other hand, fixes vulnerabilities by extracting crash constraints, using these as proof
obligations for patch synthesis without relying on extensive

4414

34th USENIX Security Symposium

test suites [13]. Finally, VulnFix [48] employs an inductive inference approach, constructing patch invariants from state mutations to generate patches, starting with a single failing input.

6.2

LLM-based Vulnerability Repair

Research has explored machine learning models for vulnerability repair [9, 10, 12], with LLMs emerging as a promising
approach [50]. Pearce et al. [32] examines zero-shot vulnerability repair using LLMs, highlighting challenges in prompt
design for generating secure code fixes. While LLMs perform
well in synthetic scenarios, real-world applications reveal difficulties in creating functionally correct patches. Wu et al.
[42] compares LLMs with deep learning techniques for Java
vulnerability repair, emphasizing the need for larger datasets
and better tuning methods. Similarly, Zhang et al. [47] demonstrates the superiority of pre-trained models over traditional
methods, proposing enhancements through transfer learning
and practical strategies. Zhou et al. [51] trains a CodeT5based model using AST and CWE knowledge, while recent
work [18, 30] explore CoT prompting for patch generation.
However, most LLM-based studies rely on explicitly provided modification locations and, in some cases, precise CWE
information [51]. In contrast, S AN 2PATCH requires only a
sanitizer log, allowing the LLM to autonomously analyze
the crash log, locate the issue, and generate patches without
human intervention. Furthermore, while previous research primarily employs basic prompt engineering techniques like CoT,
more advanced methods such as ToT, which explore diverse
reasoning paths to enhance patch diversity, have remained unexplored. Our research demonstrates that ToT-based prompting not only improves patch success rates but also ensures
vulnerability fixes while maintaining functional correctness.

6.3

Prompt Engineering

Efforts to maximize the reasoning capabilities of LLMs have
been ongoing [14]. Among these approaches, prompt engineering [35] is a technique aimed at enhancing LLM performance without requiring fine-tuning. Unlike methods that
alter the model itself, which demand substantial computational resources, prompt engineering optimizes input prompts
to elicit better responses. Few-shot prompting [6] involves
providing relevant QA pairs within the prompt to guide
the model. CoT [40], a widely adopted method, improves
LLM performance by breaking down problems into sub-steps
and enabling sequential reasoning. Building on CoT, SelfConsistency [39] enhances reliability by generating multiple
solutions and selecting the most consistent one. Advanced
methods such as ToT [45] and Graph of Thoughts (GoT) [5]
extend CoT by using tree or graph structures to explore diverse
reasoning paths and identify the best solution. Additionally,
Least-to-Most Prompting [49] addresses CoT’s limitations

USENIX Association

by decomposing complex tasks into simpler subproblems,
improving generalization to harder challenges.

7

Conclusion

We presented S AN 2PATCH, a system based on LLMs that generates security patches directly from sanitizer logs using ToT
prompting. Our evaluation demonstrated that S AN 2PATCH
successfully patches 79% of vulnerabilities in the VulnLoc
benchmark, significantly outperforming existing tools such
as ExtractFix (43%) and VulnFix (51%). The system also
proved effective on our newly curated S AN 2V ULN dataset,
which consists of previously unseen vulnerabilities, achieving
a success rate of 63% and showcasing its ability to generalize
beyond the training data. Most notably, S AN 2PATCH excelled
at addressing complex memory-related vulnerabilities, successfully fixing 81.8% of buffer overflows while preserving
program functionality.

B.1

Benchmark Details
VulnLoc Benchmark

In this study, we added automated functionality tests to the
VulnLoc benchmark to improve patch validation. These tests
use unit tests provided by project developers. If any unit tests
failed in the pre-patch project, those tests were excluded
from the functional test evaluation. However, for projects
without unit tests, functionality tests could not be applied.
In such cases, we performed a more detailed patch analysis
during manual validation. The following CVEs do not have
functional tests: gnubug-19784, CVE-2016-8691, CVE-20169557, CVE-2016-5844, CVE-2017-5974, CVE-2017-5975,
and CVE-2017-5976.
